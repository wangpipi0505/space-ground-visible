### 已关闭 P2：本地路径两侧空白在新解析入口变成异常

- 位置：`backend/src/main/java/com/runisys/orbit/spacevisibility/application/ballistic/BallisticTrajectoryService.java:41`；实际触发点 `backend/src/main/java/com/runisys/orbit/spacevisibility/infrastructure/files/BallisticFileStorage.java:155`。

- Windows 上输入 `" " + 上传返回的 serverPath + " "` 时，盘符冒号因前置空格被解释为非法位置，抛 `InvalidPathException`；同一输入经旧 resolver 成功。同样的执行顺序在允许该路径串的平台还可能无法识别已登记路径，导致漏取租约。
- 实际定向复现：使用 Java 8 编译运行 `verification/runtime/T13/PathCompatibilityReviewProbe.java`，读取标准参考 CSV 并上传到新建的系统临时根。`verification/T13/review-path-compatibility.log` 实际输出 `legacyPaddedResolves=true`、`servicePlainPoints=8560`、`servicePaddedFailure=java.nio.file.InvalidPathException`，堆栈指向上述两行。
- 最小修复建议：用于文件访问和租约匹配的本地路径统一沿用 resolver 的 trim 语义；`ParsedTrajectory.sourceLocation` 仍保留调用方原标识。补回归验证带空白的已登记路径可以解析，并确实持有同一文件租约，活动期间过期扫描不会删除该文件。

复审确认：`BallisticFileStorage.java:159` 已改为 `Paths.get(location.trim())`，并补充中文兼容说明；应用服务保存的 `sourceLocation` 原串未改。新增存储回归实际获取同 ID 租约，TTL 到期时实体保留，关闭后删除并注销 ID；新增应用回归解析带空白路径的 8560 点、逐点时间与位置速度一致、两份源文件历元相差 86400 秒、全局历元不变及原串回显。`path-fix-red.log` 先实际记录两项 InvalidPathException，`path-fix-green.log` 随后 11 项、0 失败、0 错误、1 个既有权限跳过、BUILD SUCCESS。本审查还使用最终 target/classes 独立重跑原探针，`review-path-compatibility-green.log` 输出 `legacyPaddedResolves=true`、`servicePlainPoints=8560`、`servicePaddedPoints=8560`。该缺陷关闭。
