## 实施前设计与执行计划

遵循已授权规格，仅增加纯 Java `GeometryMath` 标量工具。两个既有 Vector3 保留字段、构造及方法签名：dot、norm、夹角的非退化数学委托公共主体；简单逐轴加减/缩放保留原外壳，避免为返回不同类型增加工厂/接口或临时数组。距离继续通过两侧生产链已有的差向量 norm 进入共用主体，另提供无需临时对象的两点 distance 入口。不改 DTO、JSON、CSV、太阳/阴影策略、传播模型或版本。

椭球系数和求根只保留一套标量主体，两个明确入口选择历史 SPACE / BALLISTIC 政策；不用可插拔框架。空间直接使用原 TEME/ECI 坐标；弹道旧适配器仍先按绝对旧 J2000 秒旋转 ECEF，公共工具只接收完成适配、同一时刻同一坐标系的坐标。零段先返回 false；空间 disc<0 可见、disc==0 求根且 sqrt(max(0,disc))、之后检查 inside<1-1e-12、根容差1e-10；弹道 disc<=0 可见、sqrt(disc)、不查 inside、根容差1e-9。两者真实非等价，不能合并为统一物理判据。原弹道球体单锥独立保留6371008.8m及投影端点容差1e-9、严格大于半径，数学迁入工具但不替换椭球。

SPACE 零向量夹角抛原 IllegalStateException，弹道返回 PI；共有 acos(clamp(dot/product)) 数学保留原乘加、Math.sqrt 顺序。椭球 a、b、a²、b²沿原算式计算，不用归一化坐标、hypot、FMA或新求根公式；NaN、Infinity与负零不新增清洗。

实施顺序：①冻结原 classes 独立采集向量/距离/夹角/三种 LOS 边界和 rawbits，写可复跑来源校验；②新增入口测试 RED；③最小抽取与两个生产链接线、黄金双向对照 GREEN；④受影响几何/载荷/真实弹道/拟合回归和独立 Java 工具；⑤Java8完整 package、9空间/10弹道 capture compare、完整21文件空间原版对照、50类型1174声明 ABI；⑥记录实际失败迭代、版本、包 SHA 和范围限制。

## 实际共用与兼容边界

`GeometryMath` 集中 dot、sqrt 范数、两点距离、非零夹角 acos/clamp、椭球度量内积/系数/求根、球体投影与最近点范数。原两个 Vector3 的简单加减、缩放及返回类型未改，生产载荷距离仍在原位置先产生后续姿态还要使用的差向量，再调用共用 norm；没有为距离另算一次差或增加转换对象。新增 distance 是普通 Java 可直接使用的无分配两点入口，生产距离的实际公共主体是同一 norm。旧单锥与多载荷入口仍分别选择原球体和旋转后椭球政策。

`verify_shared_calls.py` 对最终编译字节码检查 11 条调用关系：两套 Vector3 dot/norm、空间 angleDeg、旧 angleBetween、空间 LOS、弹道球体/椭球 LOS，以及两侧生产距离入口的 norm 调用；同批六个相关 class 与最终 JAR 中字节相同。工具没有 Spring、DTO、数据库、Orekit 依赖，Math/Core 方法无 `new/newarray/anewarray/multianewarray` 指令。源码层面原空间与弹道椭球各一个临时 segment 被标量差替代，原球体 segment/scale/add 三个临时对象也被标量替代；这仅是静态源码/字节码证据，**没有运行分配 profiler、吞吐或延迟基准，不声称实测性能提升**。保留原 J2000→ECEF 两个转换结果对象。

两个 Vector3 字段、构造、public 方法与 JSON 外形未改。原空间 Vector3/GroundStationGeometry 的 public javap 声明与冻结类全文相同；弹道 ABI 独立比较 [50 个原公开类型、1174 条声明/描述符](java-contract-extended-compare.json)，`differences=[]`。新/改入口的中文注释明确单位、零向量、参考系和为何保留不同政策。窗口扫描、载荷输入、太阳光照、传播/拟合主体均未修改；T19/T20没有开始。

## 失败与定位记录

1. 入口RED是预期的缺工具失败，尚未写生产主体即实际运行。
2. 首轮新3项测试中原129对黄金与516组旋转全部通过，只有额外手写“精确相切”断言失败（`geometry-green.log`）。测试用了 x=±1000000、y=a 的理想相切，但原运算得到判别式 `0x1.cp-57`，实际略正；不得把旧算法改成容差相切。独立Java8诊断记录于 `tangent-diagnostic.log`：A=`0x1.92bf37a2e6289p-4`，B为其负值，C=`0x1.92bf37a2e628p-6`。改测试特定场景为x=±a、y=a，原A=4、B=-4、C=1、disc=0，明确检验零判别式政策。独立原探针追加第130行，并逐行确认此前129行未变；原classes重采和原JAR三轮一致。未调整产品公式、原黄金已有值或容差。
3. 扩充采集的Python脚本第一次使用Windows默认GBK读取带中文异常的UTF8黄金而失败，未写新数据；随后关联定向29项运行因仍只有129行、期望130行而出现1 failure（`affected-green.log`）。修正为显式UTF8，重新完成三轮原采集后29项全通过。不能把那次29项写为通过。
4. 字节码证据脚本首次写错真实生产方法名 `isTargetVisibleForSensorStable`，查 javap/源码确认实际为 `isTargetObservableFromSatellite` 后仅修正检查名称，11条关系通过。首次日志 `shared-production-calls.log` 保留失败，最终为 `shared-production-calls-final.log`。
5. 汇总脚本首次假设PS5工具日志为UTF8，遇`FF FE` BOM解码失败；按实际BOM使用UTF16解码后生成严格回归摘要。仅证据读取修复，无产品变化。
