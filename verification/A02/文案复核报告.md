## I07 / P2：目标查询把三个仅绑定的兼容字段描述为生效约束，并凭空增加非负拒绝规则

**位置：** `docs/接口文档.md:2507`、`:2508`、`:2509`；`docs/openapi/openapi.json:4957`、`:4960`、`:4965`、`:4972`；生成源 `verification/A02/build_contract.py:145`—`:147`、`:415`。

`POST /api/v1/space/targets/query` 的当前说明称 planningStartTime/planningEndTime 必须成对、结束晚于开始，并按开始时间排除未发射目标、计算风险；maxApproximationDays 被描述为默认 14、非负的生效风险阈值，schema 还施加 `minimum: 0`。

实际 Controller `backend/src/main/java/com/runisys/orbit/spacevisibility/api/SpaceVisibilityController.java:170`—`:172` 直接把 `@RequestBody TargetQueryRequest` 交给 queryTargets。DTO `SpaceApiModels.java:479`—`:526` 为三个字段保留 Instant/Long 及普通 setter，没有成对或数值校验。关键行为依据是 `application/PlanningFacadeService.java:219`—`:233`：该完整方法仅读取质量、目录历元、目录下限编码、ID、国籍、名称正则和分页参数，既不读取三个兼容字段，也不调用 `resolveMaxApproximationDays`。其实际 `validateTargetFilters`（`:782`—`:789`）只校验质量和目录历元范围。

因此，在其余参数有效且绑定成功的前提下，单独提供 planningStartTime、倒置这两个 planning 时间或提供负数 maxApproximationDays，都没有这里所宣称的业务拒绝规则；这不等于跳过 Jackson Instant/Long 类型与格式绑定。当前 schema 会使客户端预先拒绝服务器原本接受的负数兼容字段，也会误导集成方以为查询结果已排除了未发射目标。

**一次修复清单：**

| 所属组件/字段 | 应准确公开的现行行为 |
| --- | --- |
| TargetQueryRequest.planningStartTime | 可绑定、可空的兼容 Instant 字段；该查询业务不使用它做筛选或风险判定，没有与另一 planning 时间成对要求。保留 date-time 类型/格式。 |
| TargetQueryRequest.planningEndTime | 可绑定、可空的兼容 Instant 字段；该查询业务不使用它，不要求晚于 planningStartTime。保留 date-time 类型/格式。 |
| TargetQueryRequest.maxApproximationDays | 可绑定、可空的兼容 Long 字段；该查询不读取、不会套用配置默认阈值，不做非负业务校验；移除本组件的 minimum=0。 |
| 这三个字段的源注释 | 与现行方法不符的旧 Javadoc 不应继续追加到公开合同；可采用 M03 同样的历史注释标记，原 source-inventory 留存。 |

不能全局删除同名字段规则：`VisibilityPlanRequest.maxApproximationDays` 在 `PlanningFacadeService.java:294` 调用 `resolveMaxApproximationDays`，`:822`—`:827` 实际执行 null 使用配置默认、负数拒绝；它的 minimum=0 应保留。规划真正使用的是 startTime/endTime，不应与上述查询兼容 planning 时间混为一谈。原绑定错误和既有错误格式也应保留。

## I08 / P2：筛选统计说明沿用已不存在的发射过滤，且遗漏三个实际分支的计数口径

**位置：** `docs/接口文档.md:2721`—`:2727`（主要错误为 `:2724`、`:2727`），以及父字段 `:2675`、`:2713`；`docs/openapi/openapi.json:5839`—`:5878`（主要错误为 `:5860`、`:5878`）；生成源 `verification/A02/build_contract.py:198` 及同名 maxApproximationDays 的统一说明。

epochConstraintHit 目前解释为“任务时刻和发射条件筛选后命中数”。实际 `SpaceApiModels.java:1063`—`:1069` 构造器直接执行 `this.epochConstraintHit = epochHit`。它是兼容计数字段，不代表另一个任务时间/发射筛选阶段。getter 上关于 YYDDD 的注释同样不足以取代构造器赋值与调用方证据。

`ReferenceDataService.java:281`—`:297` 的有正则和无正则两个查询分支都把 `0L, 0L` 作为 ephemerisWarningHit、maxApproximationDays 传入统计构造。因此查询响应这两项为 0，并不表示查询实际使用了 14 天阈值或已扫描出零风险。`PlanningFacadeService.java:308`—`:321` 才分别填入本次风险清单数及实际阈值；其中显式 targetIds 快照分支把五个候选计数都设为 selectedTargetCount。当前字段说明无条件称其为逐层目录筛选结果，不能说明快照分支。

**一次修复清单：**

| 字段/语境 | 查询或无显式 ID 的兼容目录规划 | 显式目标 ID 快照规划 |
| --- | --- | --- |
| belongsHit | 国籍等前置目录条件后的数量；随后按既有质量、目录历元、名称排除逐层统计 | selectedTargetCount |
| weightHit | 叠加质量条件后的数量 | selectedTargetCount |
| epochHit | 叠加实际目录历元条件后的数量 | selectedTargetCount |
| epochConstraintHit | 恒等 epochHit 的兼容输出，无单独发射/任务时间过滤 | 恒等 epochHit，即 selectedTargetCount |
| excludeHit | 名称排除后的候选数量，不是最终传播成功数 | selectedTargetCount |
| ephemerisWarningHit | 查询固定 0（未在查询中计算）；目录规划为风险清单数量 | 风险清单数量 |
| maxApproximationDays | 查询固定 0；目录规划为本次实际风险阈值 | 本次实际风险阈值 |

目录逐层统计的实际依据为 `ReferenceDataService.java:340`—`:354`：belongsHit、weightHit、epochHit 三次 countTargets；excludeHit 由调用方传入。快照依据为 `PlanningFacadeService.java:295`—`:321`：非空 targetIds 使用 findTargetsByIds，随后 selectedTargetCount 填入五个数量。风险名单之后仍逐个构建轨道并尝试两端传播，失败另记 skippedPairs（`:334`—`:345`），所以这些候选数量不能当成传播成功数量。

相应两个父字段的概括应覆盖目录筛选和显式快照语境。M03 所修“星历风险不硬排除”仍是正确的，保持不变；本项补的是同一字段组件中遗漏的实际分支。无需修改任何响应字段、数值或 A01 样例。
