## Important

### I01 [P2] 三轨迹请求把 Java 初始化值误声明成 HTTP 默认值

- 位置：`docs/openapi/openapi.json:6663`、`:7386`、`:7426`；`docs/接口文档.md:2896`、`:3032`、`:3044`；生成来源 `verification/A02/build_contract.py:302`。
- 问题：FitRequest、SimulationRequest、RetimeTrajectoryRequest 的 `outputDir` 都声明 `default: "."`，人读表也显示“缺失=\".\"”。同一字段说明又正确指出 HTTP 未提交字段会分配管理 results 独占目录，两者相互冲突。
- 依据：未改 `BallisticFitController.java:50`、`BallisticSimulationController.java:38`、`BallisticRetimeController.java:38` 均传递 `body.has("outputDir")`；`BallisticFitService.java:34` 根据是否提交切换管理工作区。调用方或生成客户端补入机器默认值 `"."` 会改变分支，并可能令结果无法登记下载。
- 修复：从这三个 HTTP schema 删除 `default`，把 Java DTO 初始化值放到明确的说明或扩展元数据；人读“缺省”列应写缺失时自动分配管理目录。补本项小静态检查，防止再把存在性敏感字段的内部初始化值当 HTTP 默认。

### I02 [P2] 下传三个必填数组错误地允许 null

- 位置：`docs/openapi/openapi.json:5035`、`:5072`、`:5082`；`docs/接口文档.md:2524`、`:2529`、`:2530`；生成来源 `verification/A02/build_contract.py:403`。
- 问题：`DownlinkPlanRequest.satelliteIds/stations/links` 同时是 required、minItems=1 和 nullable=true。当前 schema 因此接受显式 null，人读表明确写“可null=是”。`minItems` 不会使 null 变成非法数组。
- 依据：未改 `PlanningFacadeService.java:114`、`:119`、`:950` 分别明确拒绝这三个数组为 null。生成器最初按可选引用加 nullable，后补 required/minItems 时没有同步移除 nullable。
- 修复：将三者设为不允许 null，并对缺失、null、空数组、有效非空数组分别做限定静态核验；不得改产品校验来迁就 schema。

### I03 [P2] 标准载荷范围限制被无条件施加到旧中文兼容分支

- 位置：`verification/A02/build_contract.py:344`；`docs/openapi/openapi.json:6556`、`:6564`、`:6607`。
- 问题：共享 `PayloadDef` 的 minDistanceKm/maxDistanceKm 无条件 minimum=0，sunAvoidHalfAngleDeg 无条件 0..180。但该组件同时服务旧中文四类，旧分支不读取这些标准字段。这会让 OpenAPI 提前拒绝旧实现可以绑定并忽略的值，例如旧中文 payloadType 附带 minDistanceKm=-1。
- 依据：未改 `VisibilityRequest.java:313` 根据 isStandard 二选一；旧分支仅传 payloadType/maxDetectRangeKm/sunExclusionAngleDeg，标准字段只在 `:326` 的 toStandardConstraint 读取。当前文档声称保留原兼容分支，不能额外增加此拒绝规则。

### I04 [P2] Javadoc 提取跨字段，74 个字段说明混入相邻源码及含义

### I05 [P2] 保存日志改变原字节，四份 stdout 与记录 SHA 不一致

- 位置：`verification/A02/run_verification.py:25`、`:27`；`verification/A02/commands.json:17` 起的 stdoutSha256 与对应文件。
- 问题：记录器对 `p.stdout` 求 SHA，却先 decode 后用 Windows `write_text` 保存。原 CRLF 被再次换行转换成 CRCRLF，所以保存的“原输出”不是所绑定的原始字节。
- 2026-10-14T01:15:32.922735+00:00 的只读核验结果：

| stdout | 保存字节数 | 与 commands.json SHA 一致 | CRCRLF 数量 |
| --- | ---: | --- | ---: |
| curl-version.txt | 370 | 否 | 4 |
| generate.txt | 52 | 否 | 1 |
| curl-transport.txt | 244 | 否 | 6 |
| contract.txt | 677 | 否 | 28 |
| compile.txt | 0 | 是 | 0 |

- 5 份空 stderr 的 SHA 全部一致。01:16:41 UTC 的第二个限定静态检查确认，上述四份非空文件仅将 CRCRLF 恢复为 CRLF 后，其 SHA 均与记录一致；这定位到了记录器换行转换，没有重新执行原命令。
- 修复：使用 `write_bytes(p.stdout/p.stderr)` 保存原输出，SHA 绑定实际保存字节。修复后重建本项必要验证证据，核对所有命令日志和 manifest，不得把当前四份不一致日志继续称为原字节保存。

### I06 [P2] 下载成功响应未覆盖实际支持的动态媒体类型

- 位置：`docs/openapi/openapi.json:2833`；生成来源 `verification/A02/build_contract.py:539`；人读下载状态表 `docs/接口文档.md:1773`。
- 问题：成功 content 只列 application/octet-stream 和 text/csv；实际上传接受合法媒体类型并按登记值下载，text/plain、Excel MIME 等也是有效二进制响应。文字声称 Content-Type 来自登记，机器合同却只覆盖两种。
- 依据：未改 `BallisticFileController.java:40` 接收上传类型，`:70` 原样设置登记的响应类型；`BallisticFileStorage.java:428` 至 `:432` 只拒绝控制字符/非法媒体类型，没有限制为两种。TXT/Excel 又是正文明确支持的文件格式。
- 修复：在成功响应 content 中使用实际动态类型的通配媒体范围（binary schema），可保留常见具体类型示例；不要新增服务端媒体类型限制。核验下载类型时按实际响应头匹配媒体范围，而非假定永远取第一个 content。
