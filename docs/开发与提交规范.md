# 开发与提交规范

创建日期：2026-10-13  
适用项目：空间目标与弹道目标工具合并  
适用范围：前后端新编写、迁入和修改的业务代码、测试、脚本、配置说明及 Git 提交  
关联台账：[待办事项台账](待办事项台账.md)

本规范根据用户要求制定。所有代码事项在功能/精度测试通过后，还须完成中文注释、代码规范及提交内容检查，才能更新台账为已完成并执行下一条。当前只制定规范，实施仍等待用户确认。

## 中文代码注释

- 类、接口和前端组件说明职责、调用方式、输入输出和主要依赖；重要公开方法/函数使用中文 Javadoc 或 TSDoc/JSDoc。
- DTO、接口类型、重要配置及算法参数说明含义、单位、是否必填、默认值、有效范围和特殊值。已有 JSON 字段和类型兼容约定不得因命名规范调整而改变。
- 轨道和弹道算法详细说明模型、关键公式/推导依据、积分/采样方式、时间基准、输入输出坐标系、位置速度单位、精度/容差、事件与边界处理；数学公式配中文解释。
- 载荷计算说明距离、LVLH 方位/俯仰、角速度、太阳回避的含义与判据；明确 null、0、-1、启用/禁用及启动角速度当前仅为元数据的规则。
- 窗口扫描、区间合并、稳定弧段、累计时长及最优偏移选择说明策略、顺序、并列值处理和兼容理由。
- 插值、原始点硬约束、端点修正、外推和重定时说明算法之间的关系，特别注明 ECI/ECEF 位置和速度约定。
- 缓存、可变状态、线程隔离、任务取消及文件生命周期说明线程安全边界、清理条件和失败处理。
- 前端说明组件/页面职责、props/emits、数据流、表单校验、服务端与浏览器文件引用、状态转换、API 错误和非显然的交互处理。
- 关键测试说明场景、基准来源、断言意图和容差依据；复杂构建/配置/脚本说明用途和约束。
- 注释使用中文，技术标识符、HTTP 路径、数学符号及 @param/@return/@throws 等标准标记保留原语法。迁入的业务说明注释按同样要求整理，更新代码时同步更新注释。
- 注释应充分解释行为和原因；以职责、参数、算法、边界和兼容说明为主要内容，不用重复赋值/返回语句的逐行注释代替详细说明。

## 后端 Java 与 Spring Boot

- 保持 Java 8、Spring Boot 2.7.18、Orekit 12.0 和空间软件现有构建/分层约定。
- 使用标准 Maven src/main/java、src/main/resources、src/test/java 目录，api/application/domain/infrastructure 各层按现有项目职责组织。
- Controller 处理 HTTP、DTO 和边界校验；应用服务编排流程；领域算法与工具处理数值逻辑；基础设施负责数据库、存储和配置。算法类不创建桌面 UI 或承担 HTTP 文件传输。
- 包名使用小写；类/接口使用 UpperCamelCase；方法/变量使用 lowerCamelCase；常量使用 UPPER_SNAKE_CASE。兼容类名、公开签名与接口字段按冻结合同保留。
- Java 使用 4 空格缩进，花括号和 import 顺序与空间软件现有风格一致；业务源文件使用 UTF-8，源文件行尾/空白规则由项目格式配置统一。
- 优先使用明确类型和小职责方法；避免原始泛型、无说明的魔法数、空 catch、静默失败和跨请求全局可变状态。
- 数值常量命名包含必要单位/含义，有限数、范围和特殊值在适当边界校验；错误处理保留原接口语义。
- 检查编译、适用单元/HTTP/算法回归和 Maven 打包，规范整理不能改变算法模型或精度行为。

## 前端 Vue 与 TypeScript

- 保持 Vue 3、TypeScript、Element Plus、Vite 与实际依赖锁文件，页面/组件延续现有项目模式。
- 页面、共用组件、API 调用和类型分别放入对应目录；API 请求/响应和组件边界明确类型，按现有 TypeScript 配置完成检查。
- Vue 组件和类型使用 UpperCamelCase，变量/函数使用 lowerCamelCase；组件输入、事件及表单模型命名一致，接口字段按后端合同原样映射。
- Vue/TypeScript/JSON 使用 2 空格缩进，源文件使用 UTF-8；格式配置遵循空间前端现有风格。
- 不用无依据的 any、类型强断言或重复请求掩盖问题；跨页面共用载荷/结果逻辑按实际需要复用。
- 浏览器处理文件上传、下载和预览，服务端文件引用保持独立；前端不能把本机绝对路径当作服务端输入。
- 明确加载、执行、成功、失败、取消等实际状态，界面数据与接口结果一致；复杂响应转换和兼容行为补充中文注释。
- 检查类型/构建、适用组件测试与浏览器流程，格式检查不能代替功能验收。

## Git 提交格式

统一格式：

```text
类型(范围): 中文说明 [事项编号]
```

- 类型采用标准前缀：feat、fix、docs、style、refactor、test、perf、build、ci、chore、revert。
- 范围必须使用 前端、后端 或 前后端，范围与实际改动一致。
- 仅前端业务改动使用 前端；仅后端改动使用 后端；同时修改两端、共用工程配置或项目级规范/台账文档使用 前后端。
- 功能事项附带的测试、文档和台账更新跟随该事项的实际范围，不因附带 Markdown 就把纯后端/前端事项改成前后端。
- 标题和正文的说明使用中文。类型前缀、技术标识符、接口路径、验证命令及事项编号可保留原文。
- 标题说明一个具体改动，正文按复杂度说明原因、改动内容、影响和实际验证。一个提交围绕一个台账事项或该事项的一次必要修复，不混入无关改动。
- 事项编号使用 T01—T30；后续底座阶段启用后使用 D01—D06。修复提交注明原事项及修复轮次，便于对应报告。
- 提交前完成适用测试、中文注释和规范核验，使用 git diff --check 检查空白错误；只提交预期文件和真实验证记录。

示例：

```text
chore(前后端): 初始化独立 Web 工程和开发规范 [T01]
refactor(后端): 抽取轨道外推工具并保留原传播模型 [T10]
feat(后端): 接入弹道可见窗口计算 [T14]
feat(前端): 增加弹道文件上传与可见弧段展示 [T22]
fix(后端): 修复多目标历元串扰 [T26]
test(后端): 补充拟合原始点硬约束回归 [T15]
docs(前后端): 更新部署说明和精度验收报告 [T29]
```

提交正文示例：

```text
feat(后端): 接入弹道可见窗口计算 [T14]

原因：将原弹道窗口能力纳入统一 Spring Boot 服务。
改动：接入多目标多载荷搜索，保留原偏移顺序和结果结构。
验证：填写本次实际执行的命令、测试结果及报告路径。
```

正文示例只说明写作格式，实际提交须记录已执行的验证；未执行或失败的检查不得写为通过。

## 每条事项完成前的检查

1. 实现覆盖当前事项和全局约束，接口与数值行为符合冻结标准。
2. 前后端职责、类型、命名、目录、格式及对应代码规范核验通过。
3. 相关类/组件、方法、字段、核心算法及边界有足够详细、准确的中文注释。
4. 适用测试/精度对照/浏览器流程通过，证据已保存；问题已修复并复测。
5. 提交类型、范围、中文说明、事项编号和验证正文正确。
6. 更新台账状态和实际记录，完成对应提交后再进入下一条。

所有规范检查均针对实际变更；不得以补充注释或格式整理为由顺带重写已验证的数值算法。
