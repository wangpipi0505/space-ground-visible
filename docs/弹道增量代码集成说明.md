# 已集成空间目标系统的弹道增量代码集成说明

## 一、当前两条计算链路

当前工程按原约定保留弹道数值实现，公共数学、时间、载荷判据、区间处理和外推查询入口已经抽取。空间和弹道的业务流程分别为：

```text
空间目标：api/space/空间控制器
        → application/space/空间规划服务
        → domain/space/专有模型与规则 ＋ domain公共能力

弹道目标：api/ballistic/正式控制器
        → application/ballistic/应用服务
        → domain/ballistic/visibility、trajectory、propagation实现
          ＋ domain/中的公共依赖
```

空间窗口规划同时涉及application的任务编排和domain的计算；domain.ballistic中的弹道实现也调用domain公共代码。对已经接入空间功能的系统，推荐沿用现有空间模块，增量加入弹道入口、应用服务、计算实现、文件管理及下列公共依赖。

本说明以交付工程为集成源，以用户提供的原空间目标源码作对照。集成方已经自行修改的同名公共类，应按其实际版本对照合并。

## 二、完整弹道Web功能需要迁入哪些代码

以下路径相对于backend/src/main/java，按现有Java包名迁入：

| 目录 | 文件数 | 集成内容 |
| --- | --- | --- |
| com/runisys/orbit/spacevisibility/domain/ballistic/ | 10 | visibility窗口七类、trajectory拟合器及propagation两类实现 |
| com/runisys/orbit/spacevisibility/api/ballistic/ | 11 | 窗口、拟合、模拟、重定时、文件和载荷HTTP入口，请求/错误DTO及异常转换 |
| com/runisys/orbit/spacevisibility/application/ballistic/ | 8 | 目标文件读取、窗口输入视图、计算与文件操作编排，以及contract文件用例契约 |
| com/runisys/orbit/spacevisibility/infrastructure/ballistic/files/ | 4 | 文件配置、地址解析与下载、上传/结果/临时文件及元数据存储、文件异常 |

以上33个文件共同组成当前弹道功能。domain.ballistic.visibility中的窗口辅助类按包内可见性与OrbitCalculator协作，集成时保持其包结构。API请求与领域输入共享字段定义，应用层通过BallisticVisibilityInput接收窗口参数，领域计算及窗口应用服务不依赖HTTP请求/控制器。

### 2.1 公共依赖清单

另外需要15个公共domain文件。下表的“新增/已有”以用户提供的原空间工程为对照：

| domain子目录 | 新增公共文件 | 原空间工程已有类型 |
| --- | --- | --- |
| geometry | GeometryMath、LegacyJ2000Frames | Vector3 |
| orbit | OrbitDefinition、OrbitPropagationTool、OrbitState、OrbitTime | — |
| payload | PayloadConstraintMath、StandardPayloads | PayloadConstraint、PayloadType |
| time | LegacyJ2000Time | — |
| window | SampledStateRuns、WindowIntervals | TimeInterval |

因此，以该原空间版本为基础，实际是新增44个Java文件，沿用4个已有公共类型：

- PayloadConstraint、TimeInterval与原空间源码一致。
- PayloadType仅增加说明注释，枚举值仍为GROUND、SPACE。
- Vector3在本交付中将点积、范数和夹角的等价数学委托给GeometryMath；其原有API可满足弹道依赖。集成方可继续使用原空间Vector3实现。

本轮隔离接入验证采用“44个新增文件＋原空间版4个公共类”，使用Java8编译并启动弹道接口。该验证证明此清单在原空间基线下闭合；集成方自身版本的兼容性以实际编译及回归为准。

## 三、合入现有Spring Boot工程

### 3.1 组件注册

若现有启动类已扫描com.runisys.orbit.spacevisibility，新增三个Spring组件目录会被发现。若宿主启动类使用其他根包，在宿主工程增加配置并导入：

```java
@Configuration
@ComponentScan(basePackages = {
    "com.runisys.orbit.spacevisibility.api.ballistic",
    "com.runisys.orbit.spacevisibility.application.ballistic",
    "com.runisys.orbit.spacevisibility.infrastructure.ballistic.files"
})
public class BallisticIntegrationConfiguration {
}
```

宿主通过自身组件扫描或`@Import(BallisticIntegrationConfiguration.class)`加载该配置。domain公共类型按Java依赖使用。

正式HTTP控制器统一位于api.ballistic，每个HTTP操作只有一份声明。domain.ballistic是普通Java计算代码，无需Spring组件扫描。

### 3.2 Maven依赖

继续使用宿主已配置的Java8、Spring Boot 2.7.18及空间功能依赖，在现有pom.xml中加入：

```xml
<dependency>
    <groupId>org.apache.poi</groupId>
    <artifactId>poi-ooxml</artifactId>
    <version>5.2.5</version>
</dependency>
<dependency>
    <groupId>io.minio</groupId>
    <artifactId>minio</artifactId>
    <version>8.5.12</version>
</dependency>
```

POI负责CSV之外的Excel读取，MinIO负责对应远程文件源；Spring Web和Jackson由宿主的Web工程提供。随包Maven库可按[源码包说明](../源码包说明.md)供离线构建使用。

### 3.3 文件配置

将以下配置合入宿主配置，BALLISTIC_STORAGE_ROOT设为服务可写的数据目录：

```yaml
ballistic:
  files:
    root: ${BALLISTIC_STORAGE_ROOT:storage}
    max-bytes: 67108864
    ttl-millis: 86400000
    cleanup-interval-millis: 60000
    preview-max-rows: 500
```

该目录下管理uploads、results、temp和metadata。BallisticFileConfiguration提供multipartConfigElement及定时清理支持；若宿主已有MultipartConfigElement，应合并Java Bean定义及Servlet上传参数，最终保留一个MultipartConfigElement Bean。当前模块无条件注册该Bean，仅合并YAML不足以消除同名冲突或多个同类型候选。统一后的上传限制与本模块max-bytes一致，请求总上限另留65536字节用于multipart头部。

弹道文件登记使用磁盘元数据。此次弹道增量不要求新增空间数据库表，继续沿用宿主现有空间数据库和迁移流程。

### 3.4 宿主接口约定

窗口接口通过StreamingResponseBody写出原JSON，拟合/模拟/重定时返回原FitRunResult，健康检查返回文本OK，下载返回文件内容。宿主的统一响应包装应跳过本说明列出的11个操作，保持各自的JSON层级、文本和文件返回方式，并将路径纳入现有网关、鉴权及上传下载配置。

计算控制器内部捕获的失败保留原有`{error}`；MVC绑定等控制器外异常由宿主全局Advice处理。本交付工程的ApiExceptionHandler在该边界可返回500及`{code,error,requestId}`，集成时应在宿主全局处理器中按弹道路径/控制器定向核对或适配。正常调用成功的接入验证只覆盖成功流程；错误转换仍须按[完整接口文档](接口文档.md)逐类核对。文件辅助接口有自己的局部异常协议。

前端直接跨域访问时，配置准确的前端Origin并暴露Content-Disposition以读取下载文件名；同源代理可沿用宿主现有配置。

## 五、宿主业务代码内部调用

若宿主希望使用自身Controller，可注入application.ballistic中的应用服务：

| 能力 | 应用服务入口 |
| --- | --- |
| 窗口 | BallisticVisibilityService.search(BallisticVisibilityInput) |
| 102拟合 | BallisticFitService.fitPackage102(FitInput, outputDirSpecified) |
| 模拟 | BallisticSimulationService.simulate(SimulationInput, outputDirSpecified) |
| 重定时 | BallisticRetimeService.retime(RetimeInput, outputDirSpecified) |

outputDirSpecified表示原始请求JSON是否含outputDir字段，交由正式Controller处理时已正确传入。应用服务负责结果工作区、自动登记与资源生命周期。领域输入类型位于domain.ballistic.trajectory.TargetTrajectoryFitter，HTTP请求类型位于api.ballistic.BallisticTrajectoryRequests并继承对应领域输入；窗口HTTP请求VisibilityRequest实现BallisticVisibilityInput。宿主自有Controller可以绑定这些API请求，也可自行实现应用输入视图。直接调用domain.ballistic算法时，由调用方处理文件路径、输出目录和结果登记；多目标搜索必须显式传入BallisticCsvLoader，领域只解析Path/流，网络地址加载由infrastructure.ballistic.files.TrajectoryFileResolver或应用文件服务完成。

## 六、建议集成次序

1. 保留已经接入的空间业务入口和数据模型，对照迁入33个弹道文件及11个新增公共工具，复用已有4个公共类型。
2. 合并两个Maven依赖、弹道文件配置及Spring组件注册，编译并检查上表11个操作的注册情况。
3. 联调上传、预览、下载与标准载荷，再验证窗口、102拟合、模拟和重定时。浏览器上传返回serverPath后，填入ballistics[i].csvPath；单目标兼容字段为ballisticCsvPath。
4. 用相同输入复测已接入的空间流程及弹道计算，核对UTC、坐标、CSV格式和窗口结果。

本轮验证使用用户提供的原空间源码作基线，尚未读取集成方自身工程。实际定向补丁可在集成方版本上按本清单生成和验收。

## 七、从前一交付版升级

用本版四组弹道目录替换前版对应实现，删除前版com/tx/alg目录并更新宿主Java import；从A17升级还需将窗口/拟合/传播引用迁入各自子包，文件用例契约迁至application.ballistic.contract。HTTP路径、JSON字段及CSV格式保持。此处是Java源码包归属调整，不提供旧FQN二进制兼容类；已经集成的空间业务继续保留，仅按公共依赖清单核对同名类。外推工具和数值模型沿用现有实现。

本轮A18以44个新增文件与原空间4个公共类重新完成离线编译、11项操作唯一注册及正常调用；验证清单与测试报告位于仓库verification/A18。

空间业务整体采用新包布局时，另见[空间与弹道代码集成说明](空间与弹道代码集成说明.md)。弹道增量依赖闭包不引用application.space或domain.space，可以独立接入已完成空间集成的系统。
